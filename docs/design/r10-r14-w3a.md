## F12 (`alt_screen_mouse_reporting` never passed): likely a TEST fault

By reading, not proven. X11 clicks 60 px below the OCR'd banner; the program's block is two rows tall, so the click is outside it and is not
reported. Wayland sweeps `x = window left + 140`, which is inside the vertical tabs panel in the owner's layout. `wheel_scroll` clicks on the
banner word itself. If its click arm passes where the old case fails, F12 is the old case's placement. The old case is not changed here.

## Rejected

- Adding a Rust trace hop for the link open. Every arm has an effect to judge (the recorder's argument, drawn text), so no hop is needed and
  nothing in the app changes.
- Forcing `code.editor.open_file_editor` for the path arm. The value's TOML form could not be confirmed without a build, and a wrong value in
  the settings file is worse than judging both outcomes.
- Switching the app's find hook on for Linux. `app.py` sets `PHOSPHOR_APPCI_FIND_FILE` only in the Windows launcher, so on Linux every position
  has come from OCR (r12a rows carry "app find hook gave no position"). Turning it on changes where the passing pointer cases click, with
  hook coordinates that no Linux run has checked (sway `rect` against the title bar). Recorded as a harness finding; not done in this branch.
- A plain-click control for the links. A plain click opens the link tooltip, whose place is not known, over the rows the next click needs.
  The control is instead: the recorder is empty after printing and hovering, and each link has its own token, so a wrong or doubled open fails.

## Risk

- OCR is the position source on Linux. A read that finds none of a case's words is UNVERIFIABLE, never a pass.
- Wayland: Ctrl / Shift are held by a second `wtype` while the virtual pointer clicks. If the modifier does not reach the click the link arms
  fail; the failure text says so and names the screenshot.
- `link_and_path_click` relaunches the app twice (traced, then normal). Without a working `strace` the case is UNVERIFIABLE for the
  no-connection claim (the links are still judged).

## Found by reading (not in the cases' reach)

- With no PRIMARY selection on the display, `LinuxClipboard::write_to_primary_clipboard` falls back to CLIPBOARD, so a selection overwrites
  the clipboard although `terminal.copy_on_select` is off. Filed as #2081; the case SKIPs on such a display and says why.
- The find hook is never on in a Linux or macOS run (see Rejected). Filed as #2082.
