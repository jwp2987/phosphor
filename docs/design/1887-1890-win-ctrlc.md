## #1890: keys typed after a ^C that skips a PowerShell setup

After the ^C is written the hold is `AfterAbort` and the keys typed meanwhile wait in the `PowershellSetup` gate. They used to leave only on the
shell's read marker, or, with no marker, as text at the 5 s `POWERSHELL_ABORT_MARKER_GIVE_UP` / 0.5 s settle net.

1. The `Precmd` handler (`terminal/view.rs`) counts every `Precmd` it handles (`precmd_events_seen`). Writing the abort records the count
   (`powershell_ctrl_c_precmd_count`), like `powershell_abort_marker_count` does for markers. A `Precmd` handled after the ^C, with the active block not
   executing a command, ends an `AfterAbort` hold through `end_powershell_abort_wait`, which runs `release_subshell_setup_held_bytes` and closes the gates in
   typed order. A `Precmd` counted before the abort is stale and releases nothing (`powershell_prompt_follows_ctrl_c`).
2. `StopProfiles` (hold `ScriptRunning`) is unchanged: the ^C is written and the hold stays. It now also records the count and sets
   `powershell_stop_profiles_sent`. A `Precmd` handled after it, while the hold is still `ScriptRunning` (no `Bootstrapped`: the setup died), ends the hold
   the same way and releases the keys in order. `Bootstrapped` or a new setup clears the flag.
3. Nets unchanged: 5 s marker give-up, 0.5 s settle, 30 s quiet net, 120 s ceiling. They hand keys back to the editor as text. `PowershellSetup` stays
   `SignalThenKeepGate` (`input_queue/gates.rs`), not `SignalThenRelease`. No new timer.

Not changed on purpose: the marker path (`powershell_abort_acknowledged`) still releases on the shell's read marker.

## #1887: a ^C behind a big paste on ConPTY

The ConPTY pipe takes one overlapped write at a time; a 64 KiB paste is one write, and a ^C queued behind it waited for the whole of it.

1. `EventedPty::max_write_chunk(&self) -> Option<usize>`, default `None`. The Windows `Pty` returns `Some(CONPTY_MAX_WRITE_CHUNK)` = 4096, a starting value:
   the `ctrl_c_behind_big_paste` case measures it and decides.
2. `pty_write` offers `remaining_bytes()[..min(len, N)]`. The partial-write loop already handles short writes; `Writing.written` stays the byte offset into
   the whole entry, so `cut_inside_bracketed_paste` / `push_paste_close` keep working. The `pty_write_partial` hop compares against the offered size.
3. Q-A2: `queue_input` puts a signal byte (^C ^D ^Z ^\) ahead of the typed-class entries (`UserKey`, `Paste`, `UserCommand`) queued before it, but behind
   replies, setup chunks and agent writes: it is inserted after the last non-typed entry. The close of a cut bracketed paste is a barrier too (a ^C ahead
   of it would be read as pasted text). A part-written typed entry is set aside (`State::parked`, offset intact) while a waiting ^C goes out between two of
   its chunks, then resumed first; this happens only for a pty with a chunk bound and never inside an open bracketed paste (the app's discard cuts and closes
   such a paste). No byte is dropped or duplicated. A discard or abort of the parked class drops the parked entry like the in-flight one.

Known limit: a ^C queued behind an earlier reply waits for the in-flight entry as before (the reply is ahead of it).
