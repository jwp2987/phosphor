## The one app change

`hop=find_state event=<query|next> count=<n> focused=<index|none> scanning=<bool>`, logged from `TerminalView::handle_find_event` after a
query edit and after next / previous. The text comes from `find_state_hop_detail` (pure; unit test pins the format). It is inside the
`log_hop` closure, so nothing is read when input-order logging is off.

Rejected:

- Logging at `close_find_bar`: `close_overlays` calls it from many places, and reading the count takes the terminal model's lock. The two
  chosen places run right after code that already takes that lock.
- Logging on every `RanFind`: with the bar open that fires on each pty chunk.

Risk: with logging on, one more short model lock per Find key. With logging off, none.

## Choices that differ from the table's wording

- **T2 "a slow stream".** A background job, not a foreground one (#2080). "Scroll-to-top by key" is block-up then Home.
- **T4 "`sleep 300`, pid alive / gone".** A loop that appends a line twice a second: "alive" is the file still growing, "gone" is no growth
  for 3 s. It works in both Windows panes (an msys pid cannot be checked from Python) and a surviving loop is seen directly. On POSIX the
  tab's shell pid is checked as well.
- **T4 estimate.** The table says 3 minutes. The undo window makes each mode wait about 60 s; with the close / undo half inside that wait the
  estimate stays near 3, to be confirmed by the first run.

## Each oracle can fail

Every verdict is an exact comparison or a pure helper with a self-test that feeds it the wrong result. Controls: T1 the recalled line is not
the newest one; T2 the bottom is on screen first, PageUp must move the view, the job must print during each wait; T3 a query that is nowhere
reports 0, the neighbour word is not on screen before Find; T4 the cancel half must leave the loop beating; T5 a probe line must appear in
the history file before any row is judged.
