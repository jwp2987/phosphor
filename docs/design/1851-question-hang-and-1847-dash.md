## PART A — #1851 "Preparing question..." hang: ranked candidates

Lifecycle as read (all paths absolute under /home/winters/git/phosphor-merge/app/src):
- Placeholder: chat_stream.rs:7939-7975 yields an `AddMessages` with a fully-typed ToolCall message as soon as the first ToolCallChunk parses; the history model stores it as an `Action(AskUserQuestion)` output message. From that instant the block view shows "Preparing question..." because common.rs:277-288 / 362 keys purely on `output.messages.last()` being an `Action(AskUserQuestion)` — it does not look at the action's status at all.
- Turn end: `Finished(Done)` → `mark_request_completed` (ai/agent/conversation.rs:2222-2275) marks the exchange Finished and sets `Success` ONLY if `output.actions()` is empty (2270-2273). With actions it leaves `InProgress` and relies on the controller.
- Queueing happens only at `ResponseStreamEvent::AfterStreamFinished` (controller.rs:5576-5697): `actions_to_queue` = every `Action` message of the finished exchanges → `action_model.queue_actions` (action_model.rs:1388-1419) → per-action preprocess futures joined by `ctx.spawn(join_all)` → `handle_preprocess_actions_results` (1448-1500) → `pending_actions.push_back` → `try_to_execute_available_actions` (741-786) → executor returns `NotExecuted(NeedsConfirmation)` for an ask (execute.rs:651-670) → `handle_not_executed_action` sets `ConversationStatus::Blocked` (action_model.rs:1074-1096). That Blocked write is the ONLY thing that ever moves an ask-turn out of InProgress; the ask card renders answers only when `get_action_status == Blocked` (ask_user_question_view.rs:910-935, 927-936).
- `AfterStreamFinished` is emitted from `on_response_stream_complete` (controller/response_stream.rs:1350-1358, after the last event; skipped if `current_request_id` changed — a retry re-emits for its own stream) or from `cancel` (1127-1145). Wakeup/throttle/lost-event races in that path are not present: `spawn_stream_local` delivers events then completion in order.

### 1. (Most likely for Ollama multi-tool turns) A trailing ask masks a hung earlier action — the view mis-attributes the wait
- Sequence: one turn emits `[run_command | read_files | apply_file_diffs ..., ask_user_question]`. All are queued as one batch. `try_to_execute_available_actions` starts the front action (ExecutedAsync), then for the ask `can_start_action_in_current_phase` is false (action_model.rs:756-764) → returns with no status change. `get_action_status(ask)` = `Queued` (927-941: `running_actions.contains_key` true), conversation `InProgress` (set at 1176 by `update_conversation_in_progress_status`). The block's loading text is "Preparing question..." (common.rs:362 wins over the `get_async_running_action` branch at 375 because the ask is `messages.last()`), so the user sees a question being "prepared" while what is actually pending is the earlier tool's result.
- Why nothing ends it: the ask is re-tried only from `handle_action_result` of the running action. If that action never yields a result (the known dropped-future class the BYOP preflight comment describes, controller.rs:4113-4131 — fixed only at the NEXT request, which never comes), the turn is a true hang and the text points at the wrong tool.
- Minimal fix (event-driven, view): in common.rs reorder so `get_async_running_action(app)` is consulted BEFORE `is_last_message_asking_user_question`, or gate the ask text on `action_model.get_action_status(ask.id)` being `None | Preprocessing | Blocked`. That turns the symptom into the real one ("Running command..."), which the existing #1365 stall watcher / cancel handle. Model side: nothing new; the hang is the earlier action's.
- Test: fake-model turn `[run_command(sleep), ask]` → assert loading text is the command's, not "Preparing question...".

### 2. Preprocess FIFO parking: a stuck earlier batch parks the ask forever (true hang, survives cancel)
- `pending_preprocessed_actions` (action_model.rs:392) is only ever mutated at 1411 (insert batch) and 1456 (complete batch). `cancel_all_pending_actions` (1583-1604) drains `pending_actions` but NOT preprocessing batches; nothing else clears them (sites: 392, 503, 954, 1311, 1411, 1456).
- preprocess.rs:42-105: a completing batch is parked (`has_pending_before`, 57-69) while ANY earlier batch of the same conversation is still Pending. A batch is Pending until its `join_all` resolves. The only non-trivial preprocess futures: `RequestFileEdits` (execute/request_file_edits.rs:363-417, awaits `apply_diff_model.apply_diffs` then `rx.await`) and the document/grep/glob executors; shell/read_files/MCP/ask are `ready(())`.
- Sequence: turn N includes `apply_file_diffs` whose `apply_diffs` future never resolves (remote session, huge file, diff model stall) — or the user cancels turn N mid-preprocess (the batch stays Pending). Turn N+1 ends with an ask → `queue_actions` → its batch completes → parked behind N's → the ask never enters `pending_actions`. `get_action_status` = `Preprocessing` (952-956) → card not blocked, conversation `InProgress`, text "Preparing question...". Also same-turn: `[apply_file_diffs(hung), ask]` is one `join_all` → identical outcome.
- Why nothing ends it: no timer, no cancel path, no stream event touches preprocessing batches; `handle_preprocess_actions_result`'s "Action not found" branch (50-53) also silently returns `vec![]` (actions dropped, turn still InProgress).
- Minimal fix: (a) add `PendingPreprocessedActions::abandon_pending()` (mark all Pending batches `Done{actions: vec![]}` and drain) and call it from `cancel_all_pending_actions` and at the start of `queue_actions` for a new turn (the previous turn's batches can no longer legitimately produce cards); a late `join_all` callback then hits the "not found" branch harmlessly. (b) In the "not found" / parked branches log the parked ids at WARN with `hop=agent_action status=parked` so the fuzzer/app tests can assert "no batch parked at turn end". (c) Make `RequestFileEdits::preprocess_action` bounded by an event: the diff model should resolve `apply_future` with `Err` on session drop/cancel (not a timer).
- Test: fuzzer invariant I1 already snapshots `Preprocessing` (action_model.rs:1311-1320): add an oracle rule "a Preprocessing action with no Pending batch ahead must become pending/blocked within the same event cascade"; unit test in preprocess_tests for abandon.

### 3. `AfterStreamFinished` early `return`s skip queueing and cleanup (true hang, rare)
- controller.rs:5583-5591 (`conversation_for_response_stream` None → `return`) and 5613-5616 (`exchange_with_id` None → `return`). Both bail before `queue_actions`, before `cleanup_stream`, `unsubscribe_from_model`, and `FinishedReceivingOutput`. The exchange is already Finished-with-actions, so the conversation stays `InProgress` with the ask placeholder last.
- Trigger: `added_exchanges_by_response` lost the stream between `Finished` and `AfterStreamFinished`: `mark_completed_after_successful_split` removes it (conversation.rs:2283) — that path sets Success itself, so the old conversation is fine, but a conversation whose exchanges were pruned/evicted (compaction commit, `remove_conversation_from_memory`, `clear_conversations_in_terminal_view` 2222) hits 5613 and leaves the view's conversation InProgress.
- Minimal fix: replace both `return`s with a fallthrough that still does the cleanup block (5800-5840) and, when the conversation exists but exchanges are gone, `update_conversation_status(Cancelled or Error)` — one event, no timer.

### 4. Steer/follow-up cancellation drops the turn's actions without results (self-heals via preflight; lower)
- controller.rs:5636-5657: when `cancellation` is `Some(FollowUpSubmitted)` (KeepInProgress, conversation.rs:2404-2419 leaves status untouched) the non-empty `actions_to_queue` is discarded. The ask tool_call has no result; the follow-up request's BYOP preflight should classify it `MissingResultWithoutRepairSource` and synthesize a cancel (4113-4175). If instead it is judged `PendingToolResults` (4100-4111 returns `Err(PendingByopToolResultsError)` and sends nothing) the conversation stays InProgress with the ask last → same symptom. Worth one fake-model case: steer during an ask placeholder, assert the follow-up is sent.
- Fix if it reproduces: in the cancellation arm, call `cancel_pending_action`-style synthesis for `actions_to_queue` ids before the follow-up is sent.

Ruled out on this read: placeholder-vs-End ordering (same stream, ordered), stream completion before `Finished` (→ `is_any_exchange_unfinished` error path 5659-5676), retry races (`current_request_id` guard), subscription gaps (controller subscribes at stream creation, unsubscribes only at AfterStreamFinished).

## PART B — #1847 dash idle prompt never re-judged: design

What exists (facts):
- Judge triggers: arming (view.rs:22902 "armed"), hand-off change (14651 "handoff"), every pty output wakeup (15704 "output" inside `handle_terminal_wakeup`, 15651). A wakeup is sent for every pty read that processed bytes (local_tty/event_loop.rs:1410-1417), channel unbounded (local_tty/terminal_manager.rs:444), throttle delivers the trailing item, never drops the last one (throttle.rs:168-215). So an idle "$ " that arrives as output after the baseline DOES get a look; a 6 s silence means the look happened and judged `CookedNoPrompt`, or the prompt was on screen before the baseline.
- `new_prompt` (subshell_ready.rs:160) requires `tail == ShellPrompt && prompt_moved_since_baseline`; `moved` = position != baseline && col > 0 (view.rs:22942). Baselines: arming position (22894-22897); ReArm on a user line end (23284-23301) taken via `model.try_lock()` — when the pty reader holds the lock (exactly when it is parsing the Enter's echo) the view sets `rebaseline_pending` and re-takes the baseline AT THE NEXT LOOK (22937-22941), i.e. at the look that may already contain the new prompt. That look then has baseline == prompt position → `moved` false → `Wait(CookedNoPrompt)`, and an idle cooked shell emits nothing more: no event until the next key. This is the single mechanism in the code that swallows a freshly drawn prompt; the "tail none" in the owner's one judged line says that look was at col 0 (echo only), so also check `source=` in that `subshell_ready_judged` hop line and whether a `hop=perf_echo_wakeup` followed — if the only judge was `source=armed` the arming itself happened before "$ " and the wakeup for "$ " must have been judged (then the log filter dropped it) or the ReArm swallow above applied at that look.
- No ModelEvent exists for a hookless cooked shell reaching its prompt (model_events.rs:493-540: Precmd/BlockCompleted are hook-driven). The OS facts (`tcgetattr` ICANON, `tcgetpgrp`, slave `FIONREAD` queue) are already sampled per look in `TerminalModel::subshell_tty_sample` (terminal_model.rs:2085; subshell_tty.rs:177-194) — they are conditions, not events; polling them is a timer and is out.

Options, ranked:
1. Fix the baseline swallow (view.rs:23284-23301 / 22937-22941). Record the ReArm baseline from state the view already holds — the position of the LAST look (`armed.last_position`, to be added next to `last_tty`/`last_tail`) — instead of `try_lock`-or-defer. Drop `rebaseline_pending`. Then the look that shows the echo+"$ " compares against the pre-Enter position: `moved` true, tail ShellPrompt → `Write(None)` on that same output wakeup. Event-driven (the output wakeup is the event), no new plumbing. Risk: the last look can predate a prompt drawn just before the Enter; R1 still holds (`consumed_behind_prompt` needs `queue_empty` and `prompt_moved_since_line_end`, which gets the same last-look baseline). Test: view test — arm on dash, Enter while the model lock is held by the reader (make the test's model lock busy or set `rebaseline_pending`), feed "\r\n$ " in one burst → expect `Write(None)` and `source=output`; a second variant with two bursts.
2. Rule row for the idle-at-arming case (subshell_ready.rs:171-181, owner decision): Cooked, editor-less leader, `user.bytes_since_arm == 0`, `tail == ShellPrompt`, `tty.leader == Shell`, `queue_empty == Some(true)` → `Write(None)` without `prompt_moved_since_baseline`. R1 is trivially met (nothing passed through); the OS facts prove the shell is the reader. Covers "user ran `dash`, prompt appeared, nothing else ever happens" without waiting for an Enter. Risk: a non-prompt unterminated tail (a program's partial line) while the shell is the reader — the probe is then read by the shell, which is what we want anyway; gate on `leader == Shell` only. Tests: truth-table rows in subshell_ready tests (pure).
3. A pty-reader "drained" edge: in event_loop.rs after the read loop hits WouldBlock having processed bytes this round, send `Wakeup::Output` (or a `Wakeup::Drained` variant; `Urgent` impl unchanged, event_listener.rs:11-20). Gives one guaranteed look at the settled pane per burst. Only helps if a burst's wakeup was suppressed by the sync-output check (1410) — not dash's case; keep as a cheap belt if 1 does not fully explain the log. Risk: one extra throttled wakeup per burst; none functional.
4. Rejected: `/proc/<leader>/wchan` / `TIOCINQ` polling (a timer), a shorter give-up net (the 60 s `PRE_READY_CEILING` is correctly a hand-back only), hook-based ModelEvents (dash has no hooks).

Recommend 1 now (bug), 2 as the owner's rule decision, 3 optional.
