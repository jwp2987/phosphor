# Phosphor input-route audit (table vs legacy), branch merge/w0

Method: read `dest_table.rs` (whole), the three legacy entry points, `write_user_bytes_to_pty_inner` / `_after_paste_stage`, `offer_to_paste_queue`, `prepare_subshell_gates`, `PtyQueueHost::deliver_entry`, `paste()`/`paste_routing*`, `table::decide` + facts builder, `pane_key::route_typed`, `ssh_phase_for_facts`, `abort_enter_queue`, `signal_plan`. No cargo, no edits.

Structural fact that drives most findings: in table mode a live key with `Outcome::Pty` is written via `write_user_bytes_to_pty_after_paste_stage` (dest_table.rs:415, 483, 523, 949), skipping `write_user_bytes_to_pty_inner` (view.rs:13912-13945). The table re-creates the inner stage's checks at arrival (dest_table.rs:756-776) but NOT at delivery (`decide_delivery`, dest_table.rs:289-319) nor for pastes. Everything below the paste stage (PowerShell hold, #963 take-over, hand-off oracle, counting, scroll/selection, sync event) is shared by both routes (view.rs:14056-14291), so those are at parity.

## Ranked findings

### 1. KEY LOSS (table only) — ^Z / ^\ void the waiting Enter and everything typed behind it
- Table: `execute_arrival_signal` calls `input.abort_enter_queue` for EVERY signal class (dest_table.rs:997-1001), before the outcome match. `abort_enter_queue` (app/src/terminal/input/enter_queue.rs:1302-1328) either runs `cancel_unready_enter` (enter_queue.rs:873-882: `discard_enter_gate(.., EnterDiscard::Interrupt)`, "never a hand-back") or offers a hard-coded `EntryKind::Signal(SignalKind::Interrupt)` (enter_queue.rs:1317) whose plan for EnterVerdict/TabCompletion is `DiscardThenSignal` (input_queue/gates.rs:171-173, 252-254).
- Legacy: view.rs:11468-11481 aborts only for `is_abort_key` (^C/^D, view.rs:40173-40175); ^Z/^\ fall through and are written, the Enter and its keys stay held.
- Scenario (default mode): slow shell, type `cmd⏎` (Enter held: EnterVerdict or unready-Enter gate), type `more`, press ^Z. Table: `enter_held_cancelled by=terminal_interrupt`, `more` discarded, the enter queue sees an INTERRUPT it never received. Legacy: ^Z written, nothing lost.
- Caveat: OD-1 says ^Z/^\ "jump the queue like ^C" and the tty does flush input on SUSP/QUIT, so discarding the pane-queue keys may be intended; cancelling the unready Enter and injecting `SignalKind::Interrupt` for a ^Z is not. Minimal fix: in `execute_arrival_signal` gate the `abort_enter_queue` call on `matches!(signal, Interrupt | Eof)` (legacy parity), or make `abort_enter_queue(signal)` take the real kind and only discard where `signal_plan` says so.

### 2. MISROUTE / REORDER (table only) — a paste decides its ssh hold with the legacy derivation while the keys around it use the edge machine; every table `Hold` outcome collapses to "pty paste"
- `paste()` first runs the legacy probe `swallow_input_during_ssh_setup(None)` (view.rs:25885; body view.rs:11570-11699, which also runs the legacy refreshers `refresh_ssh_connect_gate` / `deliver_ssh_typeahead_if_ready("key")` at 11610-11615), then in table mode `paste_routing_via_table` (view.rs:25904-25905 → dest_table.rs:1174-1194) which returns only `into_input = EditorInsert|AgentInput`; `Hold(SshConnect)`, `Hold(PowershellSetup)`, `Hold(SubshellSetup)`, `Hint`, `Drop` all become `false` = pty paste. The pty paste becomes a `Paste{payload}` entry behind only its `PasteReading` gate (paste_queue.rs:3082-3139) and is delivered straight into `write_user_bytes_to_pty_after_paste_stage` (paste_queue.rs:540-549) with no H3 re-check.
- Keys in table mode take the machine's phase (ssh_edges.rs:316-327), never the derivation; step 7 exists because the two disagree (`kh_ssh_phase_disagree`).
- Scenario: `ssh host⏎`; machine phase Holding (ConnectStart/would_arm) but derivation Idle (gate not armed, `pending_now.is_none() && !drops_keys`). Type `ls` (held, H3), paste `-la`, type `⏎` (held). The paste's legacy probe says no hold, the table says `Hold(SshConnect)` → into_input=false → pty paste → delivered to the local shell / connect window AHEAD of `ls⏎`. Reorder plus misroute.
- Minimal fix: in table mode have `paste()` branch on the Plan from `paste_routing_via_table` (return the Plan): `Hold(SshConnect)` → `hold_ssh_paste`, `Swallow` → the toast, `Hint` → the card hint; and skip `swallow_input_during_ssh_setup(None)` in table mode so one phase source decides the paste and the keys around it.

### 3. SECRET LEAK (medium, table only for keys; both routes for pastes) — the R8 secret-read check runs only at ARRIVAL in table mode
- Table: arrival calls `secret_read_on_key_path_cancels_written_setup` + `prepare_subshell_gates` (dest_table.rs:774-775). Delivery (`decide_delivery`, dest_table.rs:289-319) calls neither, and its executors write via the after-stage, not `write_user_bytes_to_pty_inner`.
- Legacy: every delivered chunk goes `route_after_enter_input` → `typed_characters_on_terminal` → `write_user_bytes_to_pty` → inner (view.rs:13932-13938), so the check re-runs per delivered key.
- Both routes: pty pastes never run it (paste_queue.rs:543, 558 write the after-stage directly).
- Scenario: `cmd⏎` waits for its verdict; user types the password behind it (H5, held as Text); the setup reaches Written and the `read -s` opens during the wait. Gate opens → table delivers → if `subshell_bootstrap_announced` is still set, facts say SetupHeld → `Hold(SubshellSetup)` → `table_unexpected` → legacy body → check runs (saved by the fallback). If announced is already None while `SubshellSetupState::Written` still holds a `secret_probe` (I could not confirm the two lifecycles coincide), the entry goes D6 → pty with the setup NOT cancelled, and the setup's own bytes are later typed into the password prompt. Same for a pasted password in either mode.
- Minimal fix: call `secret_read_on_key_path_cancels_written_setup(ctx)` (and `prepare_subshell_gates`) at the top of `decide_delivery` before `build_route_facts`, and before the Paste/PtyBytes after-stage writes in `PtyQueueHost::deliver_entry`.

### 4. MISROUTE (both routes, contradicts the #1430 comment) — synced input takes over the agent's command
- `write_to_pty_for_syncing_long_running_commands` (view.rs:14302-14340) sends UTF-8 text through `typed_characters_on_terminal`; both routes then write with `takes_over_agent_control = true` (table dest_table.rs:415-419; legacy view.rs:13370 → `write_user_bytes_to_pty`), and `Intent::new` defaults `takes_over_agent: true` (table.rs:134). Only the non-UTF-8 fallback uses `write_passive_input_to_pty`. The comment at 14295-14297 says the bytes go passive.
- Scenario: pane A input-synced to B; agent drives `less` in B (alt screen, agent_in_control). Typing in A → B's #963 `switch_control_to_user(Manual)` fires (view.rs:14152-14155). Table emits `SWITCH_CONTROL_TO_USER` too (table.rs:570-576).
- Fix: for `Origin::Synced` use `Intent::passive()` in `arrive_via_table` and pass `false` to the after-stage; legacy: route the text through `write_passive_input_to_pty`.

### 5. MISROUTE (low, table only) — ^C in the connect window before the legacy gate is armed gets a raw byte, not SIGINT
- Facts `ssh_sigint_applies` / `ssh_interrupt_must_wait` / `ssh_eot_must_wait` read `self.ssh_connect_gate` as-is (route_facts.rs:228-234, 316-318). Legacy predicates lazily arm it (`refresh_ssh_connect_gate()` at view.rs:12693, 12726, 12748). In table mode the key path never arms (dest_table.rs:764-765); arming happens on events (ssh_edges.rs:197, 260; view.rs:12569) and in `begin_origin_row` (dest_table.rs:1079, agent/cli/synced-raw writers only).
- Scenario: Enter on `ssh host`, ^C before the Preexec/ConnectStart edge lands: table → `pty_control(abort)` → P2/D6 → `write_user_bytes_to_pty(^C)`; legacy → P1e `SigintForegroundToPty` (#1001: a raw ^C after auth is forwarded to the remote startup). Fix: arm in `arrive_via_table` for signals only (`if is_signal { refresh_ssh_connect_gate() }`), or make the machine arm the legacy gate at ConnectStart.

## Would shadow have caught these? No, for structural reasons
Shadow compares only the leaf `DestClass` (pty/editor/held/swallowed/dropped/hint; shadow.rs:64-80) of the legacy leaf vs the table's plan, first-wins, at the live entry points, deliveries and paste routing. It cannot see:
- side effects: #1 (`abort_enter_queue`), #3 (secret cancel), #4 (take-over) — both legs still end in "pty"/"held";
- which gate holds or the second decision at delivery — `held == held`;
- #2: in shadow mode `paste_routing_via_table` is never executed (view.rs:25904 branches on `Table`), and the facts carry the LEGACY ssh derivation (ssh_edges.rs:329-339 counts `kh_ssh_phase_disagree` separately, not as a routing disagreement), so the machine/derivation split is invisible;
- the table-only executors (`execute_arrival_signal`, `hold_arrival`, `offer_arrival_to_queue`, `execute_*`) do not run in shadow at all, so any divergence inside them (#1, #5) is untestable there. Shadow validates the pure `decide`, not the table route's plumbing.
